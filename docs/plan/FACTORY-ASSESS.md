# Assess before the next recipe

Run `CUDA_VISIBLE_DEVICES='' .venv/bin/python -m dev.factory assess --run-dir reports/factory/PILOT --base minicpm` on a completed two-arm development job. The command returns a new private directory under PILOT. Open `index.html` directly (no server). `assessment.json` carries the paired summaries, model identities and trace grid. `prefixes.jsonl` contains canonical model-message prefixes preceding recorded tool decisions on four focus tasks; the observed action is evidence, not a gold label. No weights are loaded and recorded commands are never executed. Do not use development probes as training targets.

1. Compare stock, control, treatment within each seed. Start with literal script creation, branch repair, exact-match editing, draft permissions. At the first consequential decision record task, side, zero-based event index, observed evidence, expected effect and an acceptable alternative action. A different action from the oracle is not by itself an error. Compare against a passing trace when available. Keep uncertain cases unlabelled.
2. When GPU access is explicitly restored, choose a reviewed prefix and feed the identical messages to stock and each adapter. Compare full action span, path and arguments; follow with free generation in the deployment runtime. Prefixes reconstruct canonical action text, not byte-identical original replies, missing invalid-retry turns, or tokenizer logits. Score alternatives rather than assuming only one valid continuation. Do not mix this next-action diagnostic with an end-to-end success rate.
3. Test one rescue on a fresh development fixture through the real guard: supply the correct target, or separately test literal content transfer. Hold other conditions fixed. If supplying the target rescues the job, prioritize discovery training; if literal transfer alone rescues it, propose an interface version. Keep the frozen baseline and release gate separate. No new model-facing privileges or interface version are needed for this offline viewer.
